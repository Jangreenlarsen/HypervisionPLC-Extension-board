## Færdige features

- [x] done — v0.6.0 — Fase 3 afsluttet: NVS-persistering (`lib/board_config/` + `src/config.cpp`) — schema-versioneret (§3.5, `#pragma pack`-blob med CRC16-checksum og eksplicit "aldrig nedgraderet schema"-håndtering), gemmer WiFi/PLC-IP/REST-credentials/management-token via ESP32's `Preferences`-bibliotek (NVS). Management-API-token auto-genereres (hardware-RNG, `esp_fill_random`) og vises kun én gang, ved FØRSTE vellykkede `connect`. Automatisk WiFi-genforbindelse ved boot hvis allerede provisioneret. Ny `save`-kommando (gem uden at forsøge forbindelse). REST-credentials persisteres uafhængigt af WiFi-status. Rettede undervejs to rigtige fejl (se BUGS.md): `show`/`status` viste ikke reel WiFi-forbindelsesstatus, og et fabriksnyt board printede en skræmmende (men ufarlig) NVS-fejl-log-linje ved første boot. 11 nye `board_config`-tests + øvrige opdateret (79 i alt), samt et scriptet pyserial-test der beviser ægte NVS-persistering på tværs af RIGTIGE hardware-genstarter (DTR/RTS-reset, ikke kun soft-state) — REST-credentials og en `save`'et WiFi-SSID overlevede genstart; `factory-reset confirm` ryddede dem korrekt igen.
- [x] done — v0.5.0 — CLI-udvidelse (Jan): (1) **multi-linje output** for `show`/`help` (hvert felt/hver kommando på egen `\r\n`-linje, ikke længere pipe-separeret étlinjetekst) — ny `append_line()`-hjælper i `lib/provisioning_cli/`, `MB_PROV_MSG_MAX_LEN` hævet til 1024; (2) **`rest user <navn>` / `rest pass <kode>`** — REST-API Basic Auth-credentials, ved siden af (ikke i stedet for) det eksisterende Bearer-token (designdokumentet §4.4 revideret til at acceptere begge); (3) **`status`**-kommando — systemstatus (uptime, fri heap, WiFi-tilstand/IP/RSSI), sammensat i `src/provisioning.cpp` (runtime-data, ikke hardware-uafhængig); (4) **kommando-historik** (op/ned-piletaster, ANSI-escape-genkendelse i `src/provisioning.cpp`, 8 entries ringbuffer). 34 nye unit-tests (67 i alt), alle bestået native OG verificeret interaktivt på fysisk hardware (scriptet pyserial-test, inkl. faktisk afsendelse af raw escape-byte-sekvenser for piletaster).
- [x] done — v0.5.0 — Designdokument-revision (3 bekræftede arkitekturbeslutninger, se EXPANSION_BOARD_DESIGN.md): (a) **Variant A, 2 kanaler** (§2.0, nyt afsnit) — første, simplere hardware-revision via ESP32's egne 2 frie UART-periferier direkte (ingen SPI-expander-chip), inden for §2.1's eksisterende "1-2 kanaler uden dedikeret afprøvning er OK"-margin; Variant B (8 kanaler, SPI-expander) bevares som senere/større udgave. (b) **Dual REST-auth** (§4.4) — Bearer-token OG Basic Auth (brugernavn/adgangskode via CLI) accepteres begge. (c) **Diagnostisk Modbus read/write via REST** (§4.2, nye endpoints) — supplement til, IKKE erstatning for, Modbus TCP-data-planet (§4.1), som forbliver PLC'ens høj-frekvente vej. §4.1 udvidet med et konkret register-mapping-eksempel (port+Unit-ID vælger forbindelse, PDU'en/registeradressen rejser uændret igennem).
- [x] done — v0.4.0 — Seriel provisioning-CLI koblet til rigtig hardware (`src/provisioning.cpp`, `src/main.cpp`): læser linjer fra `Serial`, kalder `lib/provisioning_cli/`, og udfører et RIGTIGT WiFi-forbindelsesforsøg (`WiFi.begin()`, DHCP eller statisk IP, 30 sek. timeout jf. §3.4.1) — testet interaktivt på fysisk ESP32-hardware (ikke kun `pio test -e native`). Lokal ekko + backspace-håndtering. Fandt og rettede undervejs en rigtig bug (`MB_PROV_MSG_MAX_LEN` for lille til `help`-teksten — se BUGS.md) opdaget ved test mod ægte seriel forbindelse, ikke af den native testsuite. Firmwaren rapporterer nu også egen version+build (boot-banner + `version`-kommando), automatisk fra `version.json` (`extract_version.py`). **Stadig mangler** (resten af Fase 3, nedenfor): NVS-persistering, management-API-token-udstedelse, firewall-allowlist-seed — kræver `config.cpp`.
- [x] done — v0.3.0 — Seriel provisioning-CLI kommando-kerne (`lib/provisioning_cli/`): tokenizer (inkl. citerede værdier med mellemrum, fx SSID'er), felt-validering (SSID 1-32 tegn, WPA2-password 8-63 tegn, IPv4, dhcp/static-mode), og tilstand for `wifi ssid/pass/open/mode/ip/mask/gw`, `plc ip`, `show`, `connect`, `factory-reset confirm`, `help` (EXPANSION_BOARD_DESIGN.md §3.4.1). Password lækker aldrig i klartekst i nogen besked (maskeret som `********`) — eksplicit testet. Erstatter en tidligere planlagt WiFi AP-mode-webside, som er droppet fra designet (§3.4: seriel/USB kræver fysisk adgang, ingen trådløs angrebsflade, ingen mode-switching-kompleksitet). 33 unit-tests, alle bestået. Hardware-uafhængig — selve NVS-skrivning/WiFi-forbindelse/reboot i `src/provisioning.cpp` følger i Fase 3 og kræver fysisk hardware.
- [x] done — v0.2.0 — Modbus RTU PDU-kerne (`lib/modbus_pdu/`): CRC16, RTU-frame-opbygning, FC-baseret svar-længde-prædiktion og svar-parsing (exception-detektion, CRC/slave-validering) for FC01/02/03/04/05/06/16. Hardware-uafhængig, genbruges af både den kommende kanal-eksekvering (Lag 2, RTU-framing) og TCP-serveren (Lag 1, MBAP i stedet for RTU-framing om samme PDU) — port af mønsteret i `reference-plc-source/src/modbus_master.cpp`. 23 unit-tests (`pio test -e native`), CRC-værdier krydsverificeret med en uafhængig Python-implementering. Bygger også rent for ESP32-target (`pio run -e esp32dev`).

## Planlagte features

**Hardware er nu Variant A (2 kanaler via ESP32's egne UART1/UART2, §2.0) for første revision — ikke Variant B's 8-kanals SPI-expander-design.** Fase-numrene herunder følger stadig §9's overordnede rækkefølge, men indholdet er justeret til 2 kanaler.

- [ ] planned — Fase 1: Hardware-bring-up (Variant A) — gateway-MCU (ESP32, IKKE WROVER/PSRAM, §2.0) + WiFi; forbind RS232/RS485-transceiver-par til UART1 og UART2; verificér én kanal kan tale Modbus RTU til en kendt slave. Firewall-allowlist (seedet med PLC-IP under provisionering) er endnu ikke implementeret — hører naturligt sammen med Fase 5's REST-firewall-endpoints, ikke Fase 3.
- [ ] planned — Fase 4: Data-plan — Modbus TCP-server på 2 porte (502-503, §4.1), testet med et standard Modbus TCP-værktøj (fx `mbpoll`) mod fysisk slave
- [ ] planned — Fase 5: Management-API (`http_server.cpp`), Jans 6 punkter fra §4.2:
  - [ ] UART-kanal-config (RS232/RS485-mode, baudrate osv.) for de 2 kanaler — `PUT/GET /api/channels/{n}/config`
  - [ ] Diagnostisk Modbus-læsning — `POST /api/channels/{n}/read` (supplement til Modbus TCP, ikke erstatning, se §4.1)
  - [ ] Diagnostisk Modbus-skrivning — `POST /api/channels/{n}/write`
  - [ ] Status på modbus-config/-operationer/generelt — `GET /api/status`, `GET /api/channels`, `GET /api/channels/{n}`
  - [ ] OTA-firmwareopdatering — `POST /api/ota`, `GET /api/ota/status` (dual-partition, `src/ota_handler.cpp` i reference-plc-source som skabelon)
  - [ ] Systemstatus — dækket af `GET /api/status` (uptime/heap/version, samme data som den serielle `status`-kommando, §3.4.1)
  - Auth: Bearer-token ELLER Basic Auth (`rest user`/`rest pass`, begge accepteret — §4.4, allerede sat op via CLI'en i v0.5.0)
- [ ] planned — Fase 2 (Variant B, udskudt): 8-kanals SPI-expander-hardware — kun relevant hvis 2 kanaler pr. board viser sig utilstrækkeligt i praksis
- [ ] planned — Fase 8 (board-siden): Robusthedstest — isoleret kanal-fejl påvirker ikke den anden kanal, genstart midt i drift håndteres uden manuel indgriben, firewall afviser IP udenfor allowlist, 24-timers belastningstest uden heap-fragmentering

Se §10 i designdokumentet for den fulde, detaljerede acceptance-kriterie-liste (skrevet til Variant B/8 kanaler — gælder analogt for Variant A's 2).
