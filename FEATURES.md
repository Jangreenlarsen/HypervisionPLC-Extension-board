## Færdige features

- [x] done — v0.10.0 — Fase 5 (fortsat): UART-kanal-config REST-endpoints (§4.2) — `GET /api/channels`, `GET /api/channels/{n}`, `PUT /api/channels/{n}/config`. (1) **NVS-skema 3** (`lib/board_config/`): persisteret pr.-kanal-config (enabled/mode/baudrate/parity/stop_bits/timeout_ms/inter_frame_delay_ms), migrationskæde v1→v2→v3 med nye tests. (2) **`lib/channel_config/`** (ny, hardware-uafhængig): `mb_is_valid_baudrate()`, JSON-bygning for `GET`-svaret og en bevidst ikke-generisk (fast skema, §4.2) JSON-parser for `PUT`-bodyen — atomisk, afviser hele requestet hvis blot ét felt mangler/er ugyldigt. 13 nye unit-tests. (3) **`modbus_channel.cpp`** læser nu config fra NVS ved boot i stedet for hardkodede 9600/RS485-værdier, understøtter live-omkonfigurering (routet gennem kanalens egen kø, så en igangværende transaktion altid færdiggøres på den GAMLE config først, jf. designdokumentets krav) og sporer pr.-kanal-statistik (total/successful requests, timeout/CRC/exception-tællere, seneste fejl — slave-ID/adresse/type/uptime). Deaktiverede kanaler (`enabled:false`) afvises øjeblikkeligt med `MB_NOT_ENABLED`, uden at røre UART'en. (4) **`http_server.cpp`**: wildcard-URI-matching for `{n}`-parameteren (ESP-IDF har ingen indbygget path-parameter-udtrækning). 142 native-tests i alt, bygger rent for esp32dev.
- [x] done — v0.9.0.3 — **Fase 4 afsluttet og LIVE-VERIFICERET.** Efter v0.9.0's implementering (se nedenfor) fandt den første rigtige RTU-test (slave 9, kanal A) tre robusthedsbugs, der fik boardet til at hænge permanent (kanal-tasken og/eller TCP-lyttesocket'en, se BUGS.md v0.9.0.3). Efter rettelse: 17+ sammenhængende, korrekte Modbus TCP→RTU-transaktioner (FC03, register 0 = 0x4616), heap stabil. Wiring/RS485-mode var korrekt hele tiden — de tre firmware-bugs var den reelle årsag til den indledende stilhed. **Kanal B er endnu ikke live-testet** (ingen slave tilsluttet endnu).
- [x] done — v0.9.0 (implementering, se v0.9.0.3 ovenfor for live-verifikation) — Fase 4-implementering: (1) **`lib/modbus_tcp/`** (hardware-uafhængig): MBAP-header-parsing/-bygning (§4.1) — Transaction ID/Protocol ID/Length/Unit ID, PDU-udtrækning med streng længde-validering. 10 nye unit-tests (125 i alt), fixture krydsverificeret mod Modbus-specens klassiske FC03-eksempel. (2) **`src/modbus_channel.cpp`** (ny): én FreeRTOS-task pr. kanal (§3.2), egen kø + semaforbaseret synkron `modbus_channel_submit()` — den ENESTE indgang fra netværkslaget (ARCHITECTURE.md regel 2). RTU-transaktionen (DE/RE-toggling for RS485, to-fase timeout) bygger på det allerede-testede `lib/modbus_pdu/` og porterer mønsteret fra `reference-plc-source/src/modbus_master.cpp`. GPIO'er fra §2.0.1 (kanal A: TX17/RX16/DIR27/MODE4, kanal B: TX18/RX19/DIR25/MODE23). Baudrate/RS485-vs-RS232 er p.t. HARDKODET (9600, RS485) — Fase 5's kanal-config-REST-endpoint (`PUT /api/channels/{n}/config`) er endnu ikke bygget. (3) **`src/modbus_tcp_server.cpp`** (ny): 2 lyttesockets (502/503), ét fast `plc_ip`-permit håndhævet FØR Modbus-parsing (§4.3, fejl-lukket hvis intet `plc_ip` sat), standard gateway-exceptions 0x0A/0x0B (§4.1) ved kanal-fejl. Bygger rent for esp32dev (`pio run`), alle 125 native-tests bestået.
- [x] done — v0.8.0 — CLI-synlighed + REST-auth-mode-valg + første rigtige skema-migration. (1) **Al config synlig i CLI'en** (Jan: "vi skal have alle data om config synlige i cli" — maskering fjernet fra `show`/`status`: WiFi/REST-adgangskoder og management-tokenet vises nu i klartekst, KUN på denne serielle CLI, aldrig via REST-API'et, §4.4/CLAUDE.md regel 6 revideret). `show`/`status` viser nu også firmware-version+build. (2) **`rest auth token\|basic\|both`** — ny CLI-kommando, lader installatøren eksplicit slå Bearer-token eller Basic Auth fra (`MB_REST_AUTH_METHOD_DISABLED`, ny, adskilt fra "forkerte credentials"). (3) **Første rigtige NVS-skema-migration** (schema 1→2, §3.5): `mb_board_config_v1_t` frosset som migrations-kilde, `mb_config_load_from_blob()` migrerer nu reelt gamle blobs i stedet for kun at have en tom kommentar om det. Verificeret på den PRÆCISE situation §3.5 advarer om: boardets allerede-gemte schema-1-config (fra tidligere sessioner) blev korrekt migreret UDEN datatab efter opgraderingen — samme WiFi/REST-credentials og management-token som før. Flere nye/udvidede unit-tests (115 i alt), inkl. en manuelt konstrueret v1-blob-migrationstest og en korruptions-test. Alt verificeret live på fysisk hardware: `curl` med Basic Auth mod et token-only-konfigureret board → `401` "metode slået fra"; Bearer-token → `200`.
- [x] done — v0.7.0 — Fase 5 (start): REST-management-API-fundament, port 8080 (ESP-IDF `esp_http_server`). `lib/rest_auth/` (hardware-uafhængig): egen base64-decoder (RFC 4648, native-testet mod Python-krydsverificerede vektorer) + `mb_rest_auth_check()` — Bearer-token ELLER Basic Auth (§4.4, dual auth-model), konstant-tids credential-sammenligning. `lib/rest_status/`: JSON-builder for `GET /api/status` og REST-fejlsvar (samme `{"ok":false,...}`-stil som PLC-repoets API). `src/http_server.cpp` kobler det til rigtig HTTP — startes automatisk ved vellykket WiFi-forbindelse. `GET /api/status` viser samme data som den serielle `status`-kommando (uptime/heap/wifi/provisioned/active_channels=2). 24 nye unit-tests (127 i alt). **Verificeret LIVE mod fysisk hardware** via `curl` over det rigtige netværk (ikke simuleret): manglende auth → 401, forkert password → 401, korrekt Basic Auth → 200 + korrekt JSON.
- [x] done — v0.6.0 — Fase 3 afsluttet: NVS-persistering (`lib/board_config/` + `src/config.cpp`) — schema-versioneret (§3.5, `#pragma pack`-blob med CRC16-checksum og eksplicit "aldrig nedgraderet schema"-håndtering), gemmer WiFi/PLC-IP/REST-credentials/management-token via ESP32's `Preferences`-bibliotek (NVS). Management-API-token auto-genereres (hardware-RNG, `esp_fill_random`) og vises kun én gang, ved FØRSTE vellykkede `connect`. Automatisk WiFi-genforbindelse ved boot hvis allerede provisioneret. Ny `save`-kommando (gem uden at forsøge forbindelse). REST-credentials persisteres uafhængigt af WiFi-status. Rettede undervejs to rigtige fejl (se BUGS.md): `show`/`status` viste ikke reel WiFi-forbindelsesstatus, og et fabriksnyt board printede en skræmmende (men ufarlig) NVS-fejl-log-linje ved første boot. 11 nye `board_config`-tests + øvrige opdateret (79 i alt), samt et scriptet pyserial-test der beviser ægte NVS-persistering på tværs af RIGTIGE hardware-genstarter (DTR/RTS-reset, ikke kun soft-state) — REST-credentials og en `save`'et WiFi-SSID overlevede genstart; `factory-reset confirm` ryddede dem korrekt igen.
- [x] done — v0.5.0 — CLI-udvidelse (Jan): (1) **multi-linje output** for `show`/`help` (hvert felt/hver kommando på egen `\r\n`-linje, ikke længere pipe-separeret étlinjetekst) — ny `append_line()`-hjælper i `lib/provisioning_cli/`, `MB_PROV_MSG_MAX_LEN` hævet til 1024; (2) **`rest user <navn>` / `rest pass <kode>`** — REST-API Basic Auth-credentials, ved siden af (ikke i stedet for) det eksisterende Bearer-token (designdokumentet §4.4 revideret til at acceptere begge); (3) **`status`**-kommando — systemstatus (uptime, fri heap, WiFi-tilstand/IP/RSSI), sammensat i `src/provisioning.cpp` (runtime-data, ikke hardware-uafhængig); (4) **kommando-historik** (op/ned-piletaster, ANSI-escape-genkendelse i `src/provisioning.cpp`, 8 entries ringbuffer). 34 nye unit-tests (67 i alt), alle bestået native OG verificeret interaktivt på fysisk hardware (scriptet pyserial-test, inkl. faktisk afsendelse af raw escape-byte-sekvenser for piletaster).

## Planlagte features

**Hardware er nu Variant A (2 kanaler via ESP32's egne UART1/UART2, §2.0) for første revision — ikke Variant B's 8-kanals SPI-expander-design.** Fase-numrene herunder følger stadig §9's overordnede rækkefølge, men indholdet er justeret til 2 kanaler.

- [ ] planned — Fase 1: Hardware-bring-up (Variant A) — gateway-MCU (ESP32, IKKE WROVER/PSRAM, §2.0) + WiFi; GPIO-allokering klar (§2.0.1); forbind RS232/RS485-transceiver-par til UART1 og UART2; verificér én kanal kan tale Modbus RTU til en kendt slave.
- [ ] planned — Fase 5 (resten): Management-API (`http_server.cpp`), Jans 6 punkter fra §4.2 — auth-fundament + `GET /api/status` + systemstatus er FÆRDIGE (v0.7.0, se ovenfor):
  - [x] done — Auth: Bearer-token ELLER Basic Auth (`rest user`/`rest pass`) — `lib/rest_auth/`, v0.7.0
  - [x] done — `GET /api/status` (= systemstatus, samme data som seriel `status`) — `lib/rest_status/` + `src/http_server.cpp`, v0.7.0
  - [x] done — UART-kanal-config (RS232/RS485-mode, baudrate osv.) for de 2 kanaler — `PUT/GET /api/channels/{n}/config`, v0.10.0
  - [ ] Diagnostisk Modbus-læsning — `POST /api/channels/{n}/read` (supplement til Modbus TCP, ikke erstatning, se §4.1)
  - [ ] Diagnostisk Modbus-skrivning — `POST /api/channels/{n}/write`
  - [ ] OTA-firmwareopdatering — `POST /api/ota`, `GET /api/ota/status` (dual-partition, `src/ota_handler.cpp` i reference-plc-source som skabelon)
- [ ] planned — Fase 2 (Variant B, udskudt): 8-kanals SPI-expander-hardware — kun relevant hvis 2 kanaler pr. board viser sig utilstrækkeligt i praksis
- [ ] planned — Fase 8 (board-siden): Robusthedstest — isoleret kanal-fejl påvirker ikke den anden kanal, genstart midt i drift håndteres uden manuel indgriben, firewall afviser IP udenfor allowlist, 24-timers belastningstest uden heap-fragmentering
